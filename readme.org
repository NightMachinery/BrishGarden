#+TITLE: Readme

A REST HTTP API for running zsh code, built on top of =Brish=.

* Install
#+begin_example zsh
pip install -U brishgarden
#+end_example

Or install the latest version directly from git:
#+begin_example zsh
pip install git+https://github.com/NightMachinery/BrishGarden.git
#+end_example

To reinstall the latest version:
#+begin_example zsh
pip install git+https://github.com/NightMachinery/BrishGarden.git
pip install --no-deps --force-reinstall git+https://github.com/NightMachinery/BrishGarden.git
#+end_example

** Requirements
- Python 3.10 to 3.13.
  - The dependency floors in =pyproject.toml= need 3.10: FastAPI 0.133 is the first release that allows Starlette 1.x, and Starlette 1.3.1, python-multipart 0.0.31 and pydantic-settings 2.14.2 are the first releases without a known advisory.
  - Python 3.14 is excluded because Brish's command templates (=brish.z=) read =ast.Constant.s=, which 3.14 removed, so every plain-text reply fails there.
  - Once a fixed Brish is released, the cap can rise to include 3.14, but not further for now. spaCy 3.8.16, which PyNight requires, needs Python below 3.15. With a looser bound, Poetry locks spaCy 3.8.2, numpy 2.0.2 and other old releases for the newer Pythons, and none of them has wheels there, so an install would compile them from source.
- uvicorn older than 0.47. From 0.47 on, uvicorn imports the app before it starts the event loop, and the garden needs a running loop when it is imported.
- PyNight with its API-key helpers (=pynight.common_apikey=), without which the garden cannot start. PyNight 0.2.5, the latest release on PyPI and the version =poetry.lock= pins, predates them, and the git version carries the same version number, so until the next release replace it with the git version after installing BrishGarden (with pip or with =poetry install=):
  #+begin_example zsh
pip install --no-deps --force-reinstall git+https://github.com/NightMachinery/PyNight.git
  #+end_example
- For binary mode (see "Binary data" below) and for the test suite, a Brish that has binary mode. Brish 0.3.6, the latest release and the version the lock pins, runs the garden in legacy mode but predates binary mode, and the git version again carries the same version number, so replace it the same way:
  #+begin_example zsh
pip install --no-deps --force-reinstall git+https://github.com/NightMachinery/brish.git
  #+end_example

* Tests
The suite in =tests/= needs a Brish that has binary mode (see "Requirements"): with Brish 0.3.6 from PyPI, some of its tests fail even in legacy mode, because they use binary mode's API (the =binary= argument of =Brish()=, binary results). It runs in two modes, legacy and binary, chosen by =BRISH_BINARY=, so run it once in each; =tests/conftest.py= gives the commands. To test an unreleased Brish checkout, put it first on =PYTHONPATH= and name it in =BRISHGARDEN_TEST_BRISH_ROOT=; the guard tests then check that it is the Brish being imported.

* security
Every endpoint requires the header =X-API-Key=. Binding to =127.0.0.1= keeps
other hosts out, but not the other users of this machine nor a browser tricked
into POSTing to localhost, and this API runs arbitrary zsh.

The key is generated on first boot into =~/.keys/brishgarden= (mode =0600=),
which holds a complete header line:

#+begin_example
X-API-Key: <key>
#+end_example

That format lets clients send it without ever putting the key in argv, which
=ps= exposes to every local user:

#+begin_example zsh
curl --header @$HOME/.keys/brishgarden --header 'Content-Type: application/json' \
     --request POST --data '{"cmd":"ec hi","verbose":"0"}' \
     http://127.0.0.1:7230/zsh/
#+end_example

Remote clients authenticate to a reverse proxy instead. Ours (Caddy) checks HTTP
basic auth and then injects this host's key upstream with =header_up=, so the
key never leaves the machine that generated it.

A request body must come with =Content-Type: application/json= (a parameter
such as =; charset=utf-8= is fine). Without it the garden replies 422 and runs
nothing, as FastAPI does by default since 0.132 (=strict_content_type=). Older
gardens parsed a body with no Content-Type as JSON, so a client that sends
none, such as Python's =requests.post(url, data=json.dumps(body))=, worked
there and fails now. The strict default is kept on purpose: a browser can send
a cross-site POST with no Content-Type and no CORS preflight (a =fetch= with a
=Blob= body). Locally, the required =X-API-Key= stops that request, but behind
the reverse proxy it may not, since the proxy adds the key itself and a browser
that has logged in to the proxy may attach its basic-auth credentials.

* API
=POST /zsh/= runs a zsh command in one of the garden's Brish workers; =POST /zsh/nolog/= does the same without an access-log line. The body is JSON, sent with =Content-Type: application/json= (see "security" above), and has these fields:
- =cmd=: the command, as text.
- =stdin=: its standard input, as text (default: empty).
- =json_output= (old name =verbose=): =0= (the default) replies with the command's output as =text/plain=, with stderr merged into stdout. Any other value replies with JSON: =cmd=, =session=, =brishes=, =allBrishes=, =out=, =err= and =retcode= (with =binary: 1=, also =out_b64= and =err_b64=, see below).
- =session=: run in a dedicated Brish of that name, created on first use, instead of the shared pool.
- =nolog=, =log_level= and =failure_expected=: control the garden's logging and its failure notification.
- =cmd_b64=, =stdin_b64=, =binary= and =b64_only=: binary data, see below.

The command =%GARDEN_ALL= restarts every Brish.

To send and receive exact bytes without JSON or base64, use the raw API (=POST /zsh/raw/=, below) instead; to get the output while the command runs, the streaming API (=POST /zsh/stream/=, below).

** Binary data (opt-in)
JSON strings cannot carry arbitrary bytes, so optional fields do it with base64:
- =cmd_b64= and =stdin_b64= hold the command and its stdin as base64 of the raw bytes. They take precedence over =cmd= and =stdin=. Whitespace inside them is ignored.
- =binary: 1= asks for the exact output. The plain reply (=json_output: 0=) is then the raw bytes of stdout followed by stderr, as =application/octet-stream=. The JSON reply adds =out_b64= and =err_b64=, the base64 of the exact stdout and stderr, next to the text fields =out= and =err=.
- =b64_only: 1=, with =binary: 1=, drops the text fields =out= and =err= from a binary JSON reply, since they only duplicate =out_b64= and =err_b64= (and, for binary data, are larger); the other fields are unchanged. It is opt-in because some clients read =out= and =err= even from a =binary: 1= request (=brishz_para.dash= under =brishz_binary=y=). It has no effect on the plain reply, on a reply without =binary: 1=, or in legacy mode, where a =binary: 1= request is refused. A garden older than this field ignores it and sends the text fields too.

#+begin_example zsh
curl --header @$HOME/.keys/brishgarden --header 'Content-Type: application/json' \
     --request POST --data '{"cmd_b64":"Y2F0","stdin_b64":"/wA=","binary":1}' \
     --dump-header /dev/stderr http://127.0.0.1:7230/zsh/ | od -c
#+end_example

Here ~Y2F0~ is =cat= and ~/wA=~ is the two bytes =\xff\0=, which come back unchanged.

Exact bytes need the garden's Brish to run in binary mode (see "Binary Data" in Brish's readme), which is the garden's default; =BRISH_BINARY=0= turns it off (see "environment variables" below). A garden in binary mode marks every reply to a =binary: 1= request with the header =X-Brish-Binary: 1= (it goes out lowercased, as =x-brish-binary=; header names are case-insensitive). Other gardens never send it:
- a garden whose Brish runs in legacy mode (started with =BRISH_BINARY=0=, or with a brish too old for binary mode) refuses a =binary: 1= request without running it, and replies with retcode 9000 and a message that says so;
- a garden older than these fields ignores them, so a request that carries its command only in =cmd_b64= gets "Empty command received." and nothing runs.

So a client that needs exact output should check for the header, and fail when it is missing: then nothing ran.

Without =binary: 1=, the =_b64= fields still deliver exact input, and the reply is the usual text reply. A garden in legacy mode accepts them only when they decode as UTF-8, since it carries text; otherwise it refuses the request before running anything. A malformed request (invalid base64, a field that is not a string) is refused the same way, with retcode 9000.

Requests without the new fields get the replies they always got, with the differences below in binary mode. From a garden in legacy mode they are byte-identical to the replies of a garden older than these fields that runs the same Brish, so =BRISH_BINARY=0= is also the way back to the old replies. In binary mode, the default, the text views are exact, so replies differ only where legacy mode lost information: a =\r= is kept, where the legacy mode of older Brish turns =\r\n= and a lone =\r= into a newline and drops a trailing =\r= (Brish's legacy mode keeps them too since its legacy backports of October 2026); and a NUL in the output no longer desynchronizes the worker. Binary mode also changes how some commands end (=exit=, NOMATCH errors, =errexit=); see Brish's readme. In both modes, a lone surrogate in a text field of the reply (a JSON request can smuggle one in with a =\udcff= escape) is escaped as text, where it used to make the reply fail.

** Raw API
=POST /zsh/raw/= runs a command like =/zsh/=, but carries bytes as bytes in both directions, with no JSON and no base64. =POST /zsh/raw/nolog/= is its variant without an access-log line (the =nolog= routes hide that line also when the URL has a query string). It needs the =X-API-Key= header like every endpoint. Its reply comes when the command has ended; the streaming API ("Streaming API", below) takes the same request and sends the output while the command runs.

The request:
- The body is the command's bytes followed by its stdin's bytes.
- The header =X-Brish-Cmd-Length= (required) gives the command's length in bytes, in decimal. The command never goes in a header, since servers and proxies limit header sizes.
- The optional header =X-Brish-Stdin: null= makes stdin =/dev/null=; the body must then end with the command. (A garden in legacy mode has no =/dev/null= stdin and runs the command with empty stdin.)
- Options are query parameters, with the meanings of the JSON fields: =session=, =nolog=, =log_level=, =failure_expected=, and =merge=1=, which merges stderr into stdout in the shell, like the JSON API's plain reply path. Boolean values follow Brish's =bool_from_str=: empty, =0=, =n=, =no= and =false= are false.

The reply is HTTP 200 for every request the garden understood, as =application/octet-stream=:
- The body is stdout's bytes followed by stderr's. With =merge=1=, stderr is normally empty, so the body is the merged stream.
- =X-Brish-Retcode= is the command's exit status, and =X-Brish-Out-Length= the length of the stdout part in bytes; the rest of the body is stderr.
- =X-Brish-Binary= is =1= when the garden runs in binary mode, so the bytes are exact, and =0= in legacy mode, where they went through text (see "Binary data" above). A legacy-mode garden still serves the raw API: it decodes the command and stdin strictly as UTF-8, and refuses anything else and any NUL (which legacy mode cannot carry) as described below.
- A notice that is not a command's output (an empty command, a magic command such as =%GARDEN_ALL=) has =X-Brish-Notice: 1=, the notice text as the stdout part, and retcode 0.
- A malformed request (no =X-Brish-Cmd-Length=, one that is not a decimal number or exceeds the body, =X-Brish-Stdin= with another value or with a stdin part, a =log_level= that is not an integer, either header or an option sent twice with different values) runs nothing and gets retcode 9000, with the message as the stderr part. So does a request whose run raised an exception, with the traceback as the stderr part, as on the JSON API.
- =X-Brish-Refused: 1= marks a reply for a request that ran nothing: a malformed request, and, on a legacy-mode garden, a command or stdin that is not valid UTF-8 or holds a NUL. A client may retry such a request another way (the JSON API, say) without running it twice. Only a refusal has the header: a command that ran never gets it, even when it returns 9000 with an error-like stderr, and neither does a request whose run raised an exception, since it may have run.

Logging, the first-seen IP notification, =log_level= and =failure_expected= work exactly as on the JSON API: both APIs share one code path, and only the decoding and the reply differ. The garden's own log line for a raw request (=IP - cmd: ..., session: ...=) ends with =, raw=; uvicorn's access line, next to it, has no such mark.

#+begin_example zsh
cmd='cat; print -rn -- done >&2'
print -rn -- "$cmd"$'\xff\0' |
    curl --silent --header @$HOME/.keys/brishgarden --header 'Content-Type: application/octet-stream' \
         --header "X-Brish-Cmd-Length: $(print -rn -- "$cmd" | wc -c | tr -d ' ')" --data-binary @- \
         --dump-header /dev/stderr 'http://127.0.0.1:7230/zsh/raw/?session=demo' | od -c
#+end_example

Here the reply body is the two bytes =\xff\0= from stdout and then =done= from stderr, with =x-brish-out-length: 2=. The length counts bytes, which =wc -c= does; zsh's =${#cmd}= counts characters.

A garden older than the raw API answers =404= for these routes, without running anything. A client can rely on that to fall back to the JSON API, knowing that nothing ran.

** Streaming API
=POST /zsh/stream/= runs a command like =/zsh/raw/= and sends its output while it runs: each piece of stdout and stderr goes out as soon as the garden reads it from the worker. =POST /zsh/stream/nolog/= is its variant without an access-log line. =brishzgo= uses it with =brishz_stream=y= (see =docs/brishzgo.md= in the scripts repository).

The request is exactly the raw API's (see "Raw API" above): the body is the command's bytes and then stdin's, with =X-Brish-Cmd-Length=, the optional =X-Brish-Stdin: null=, and the same query parameters (=session=, =nolog=, =log_level=, =failure_expected=, =merge=). The garden parses it with the same code, checks the same =X-API-Key=, and logs, notifies and plays the failure sound exactly as for the other APIs (the failure sound after a command that ends non-zero); the garden's own log line for it ends with =, stream=, as a raw request's ends with =, raw=. Sessions, the shared pool, magic commands such as =%GARDEN_ALL= and notices work as on the raw API. The whole request body is read before the command starts, as on the raw API, so stdin is not streamed into the command.

The reply is HTTP 200, =application/octet-stream=, sent chunked. Its headers go out before any output, so they cannot depend on it:
- =X-Brish-Stream: 1= marks a streaming reply.
- =X-Brish-Binary= is =1= in binary mode, where the bytes are exact, and =0= in legacy mode, as on the raw API.
- A request that runs nothing gets =X-Brish-Refused: 1= (a refusal, exactly when the raw API would refuse it: a malformed request, or NUL or invalid UTF-8 on a legacy-mode garden) or =X-Brish-Notice: 1= (an empty command, a magic command). A client may retry a refused request another way without running it twice.

The body is a sequence of *frames*. A frame is a type byte, then the payload's length as 4 bytes, big-endian and unsigned, then the payload:
- type 1: bytes the command wrote to stdout, as the garden read them (never empty);
- type 2: bytes it wrote to stderr, or a message of the garden (never empty);
- type 3, the *exit frame*: the retcode in decimal ASCII, such as =0=, =130= or =9000=.

Every complete reply ends with exactly one exit frame, and nothing follows it. A body that ends without one was cut short (the garden died, say), and the output before that point is all there is. A client should skip frames of any other type, which later gardens may add. A refusal is one stderr frame with the message and the exit frame =9000=; a notice is one stdout frame with the text and the exit frame =0=; an exception while the command ran ends the reply with its traceback in a stderr frame and =9000=. With =merge=1=, every output frame is a stdout frame, in the order the garden read the output, so the client sees one stream (the garden's own refusals and tracebacks stay in stderr frames). =brishgarden/stream.py= has the reference decoder, =FrameDecoder=.

#+begin_example zsh
cmd='print -r -- one; sleep 1; print -r -- two >&2; return 3'
print -rn -- "$cmd" |
    curl --silent --no-buffer --header @$HOME/.keys/brishgarden --header 'Content-Type: application/octet-stream' \
         --header "X-Brish-Cmd-Length: $(print -rn -- "$cmd" | wc -c | tr -d ' ')" --data-binary @- \
         --dump-header /dev/stderr http://127.0.0.1:7230/zsh/stream/ | od -c
#+end_example

Here =od= shows the frames =001 \0 \0 \0 004 o n e \n= (stdout), =002 \0 \0 \0 004 t w o \n= (stderr) and the exit frame =003 \0 \0 \0 001 3=. The first left the garden at once and the second a second later, though =od= prints nothing until its own buffer fills or the reply ends.

The output comes as the worker produces it, but a program whose stdout is a pipe may buffer its own output (C's stdio, Python without =-u=), and then sends it in bursts; the garden adds no buffering of its own. A reverse proxy that buffers responses delays the frames too; this was tested only on =127.0.0.1=.

*Disconnects.* When the client goes away before the command ends (it closed the connection, or it was interrupted: =brishzgo= closes the connection on SIGINT, SIGTERM and SIGHUP), the garden starts to kill the command at once, with Brish's =BrishPopen.kill=, reads what is left of its output and drops it, and gives the worker back once the command has ended. The garden logs one info line with the retcode the command ended with, and neither the failure log nor the failure sound: the client asked for the end. A request whose client goes away while it still waits for a worker (every pool worker is busy, its session runs another request, or a new session's worker is still starting) runs nothing, and its info line says so. This is the one API where the client's going away stops the command; the JSON and raw APIs run it to its end, since they only write to the connection once they have the whole reply.

The kill has up to four steps, and stops at the first one after which the command has ended. Each step comes about 2 s (Brish's =kill_grace=) after the one before, or about 4 s while the command keeps writing; on a loaded machine the =ps= run of each step makes them later.
1. SIGINT to the worker, then to the processes below it.
2. SIGINT to the worker again, and SIGTERM to the processes below it.
3. SIGKILL to the processes below the worker.
4. SIGKILL to the worker itself: the retcode is 9001.

Most commands end at step 1, within about 0.1 s, with 130, and the worker keeps its state, so a session keeps its variables, functions and directory. A command that traps or ignores SIGINT in the worker itself (=trap ... INT=) is not ended by steps 1 and 2: its trap runs, and each time one of its processes dies of a signal (SIGINT at step 1, unless it ignores it too, SIGTERM at step 2, SIGKILL at step 3), the command goes on with its next statement. So it can run statements after its client has gone: =trap '' INT TERM; sleep 8; print -r -- ran >> file= wrote the file about 4 s after the disconnect, when step 3 killed the =sleep=. Such a command ends only at step 4: about 4.5 s after the disconnect when nothing runs below the worker (step 3 then has nothing to kill, and the worker's SIGKILL follows at once), about 7 s when something does (as in that example), and up to about 13 s while it keeps writing. That step kills the worker, and Brish replaces it (see "When a Worker Dies" in Brish's readme): a session loses its variables, functions and directory, and its next request waits for a new worker to start (5 to 8 s after the disconnect in the tests). Steps 2 to 4 also stop background jobs that earlier commands left on that worker, since they run below it too; step 1 leaves them alone, since background jobs ignore SIGINT.

*Readers that do not read.* A client that stays connected but stops reading holds its command: the garden queues at most 256 KiB of frames for it (beyond the sockets' own buffers), and then the command blocks on its own output, as a local command does when its pipe is full. Nothing times this out, so such a command keeps its worker, and a session waits for it. =%GARDEN_ALL= does not wait for it: it starts new workers for the pool, forgets the sessions (each starts afresh at its next request), and answers once the new pool runs (about a second in the tests), while the cleanup of the old workers, which runs in the background, waits until the stalled command ends, that is, until its client reads on to the end or goes away. Backpressure keeps the garden's memory flat: a reader that took 200 MB at 1.7 MB/s kept the garden's RSS under 50 MiB, from 23 MiB before the stream.

*Owner threads.* Each open stream has an owner thread from the moment its reply starts, also while it waits for a worker: for a free pool worker, or for its session while another request runs there. They are bounded at the pool's size plus 16 (32 with the default 16 workers). Further streams wait for a thread, with their headers sent and no frames yet; the JSON and raw APIs do not use these threads. A waiting stream whose client goes away gives its thread back within 0.1 s (on a session) or 1 s (on the pool), and runs nothing. So only streams whose clients stay connected can hold every thread: when a session runs a command that does not end and 31 more connected streams wait for it, every other stream waits too, until that command ends or its client goes away. The JSON and raw APIs have the same kind of limit on the threads they share (40, Starlette's default): that many requests waiting on one busy session hold them all.

*Legacy mode* (=BRISH_BINARY=0=) streams too, with the limits of Brish's legacy transport: a NUL or invalid UTF-8 in the command or stdin is refused, the output goes through text, and Brish holds back a trailing newline until more output comes or the command ends, so a line shows without its newline until then.

A garden older than the streaming API answers =404= (FastAPI's ={"detail":"Not Found"}=) for these routes, without running anything, so a client can fall back to the raw API, and from there to the JSON API, knowing that nothing ran.

* environment variables
** =BRISHGARDEN_N= sets the number of Brishes started by default
** =BRISH_BINARY=0= runs the garden's Brishes in legacy mode
The garden runs every Brish it creates (the shared pool, the session Brishes, and the pool that =%GARDEN_ALL= rebuilds) in one mode, binary by default. It reads =BRISH_BINARY= once, when the process starts:
- unset or empty: binary mode;
- a false value (=0=, =n=, =no= or =false=, in any case): legacy mode, the text transport of gardens older than binary mode;
- any other value, such as =1=: binary mode.

So changing it needs a restart of the garden process; =%GARDEN_ALL= keeps the mode. The startup log line =Initializing N brishes in binary mode ...= names it.

Brish itself treats an unset =BRISH_BINARY= as legacy mode, and the garden leaves the variable alone: it passes the mode to each Brish as an argument instead of setting it. Commands the garden runs inherit its environment, so a Python script they start keeps Brish's own default.

With a brish too old for binary mode (its =Brish()= takes no =binary= argument), the garden runs in legacy mode and logs one warning that says so.
